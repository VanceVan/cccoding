Integration Plan — Peritoneal Dialysis Remote Patient Monitoring (PD-RPM)

1. Integration strategy

PD-RPM is integrated bottom-up, in increments, behind criterion-driven gates. Those are three of the eight techniques the module names, and they are chosen together for one reason: the system’s dominant failure mode is a fault that no single party can localize.

Global (big bang) integration is rejected outright. The risk register’s top entry, R-1 silent gateway, is exactly the class of defect that big bang cannot isolate — a record that never arrives implicates the cycler, the gateway firmware, the carrier, and the ingest service equally. Every stage below therefore adds one new class of object, so that a defect appearing at stage n is attributable to what stage n introduced.

Both horizontal and vertical integration are used, and Figure 1 labels which is which. S1, S4, S6 and S7 are horizontal: elements at a common hierarchy level joined to each other. S3, S5 and S8 are vertical: a completed level proved consistent with what the level above expects of it.

6. Early error detection

Four test points are designed in rather than retrofitted, because the module’s own lesson is that more is better: a diagnostic port on HG-1 exposing buffer depth and link state; a packet capture tap at EG-1; a synthetic record injector at IS-1; and the fleet replay sandbox built for the Module 6 team-learning review, which lets a failure be re-run without a patient.

7. Why the plan is agile, and what that buys

The plan is incremental on purpose. Increment 1 delivers a home node that buffers, Increment 2 a platform that alerts, Increment 3 the external exchanges and the pilot. Each increment is a build-a-little, test-a-little cycle that ends in something demonstrable.

Three benefits follow. Nurses see a working triage queue at the end of Increment 2, while changing it is still cheap. Each increment boundary is a genuine re-planning point, so a carrier or EHR schedule slip re-orders the remaining work instead of stalling it. And the software elements run continuous integration — daily build, automated regression — inside stages whose hardware integrates at fixed gates, which is the hybrid cadence a software-intensive medical system needs.

8. Verification, validation, and configuration control

Verification and validation are kept distinct throughout. G0 to G7 are verification: objective evidence that an element or assembly meets its specified requirements, by inspection, analysis, demonstration or test. G8 is validation: objective evidence that the system in use meets stakeholder needs, with the intended users, in the intended operational environment. The patient is the last thing added, and nothing before G8 claims the system works — only that it is built the way it was specified.
